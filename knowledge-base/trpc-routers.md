# tRPC Routers

> How tRPC routers are organized, registered, and consumed in the Cal.com codebase.

## Overview

Cal.com uses tRPC as its primary internal API layer between the Next.js frontend and feature logic. Routers are organized by domain (bookings, event types, availability, etc.) under `packages/trpc/server/routers/`. The frontend consumes them via typed React hooks generated by `createTRPCNext`.

## Key Locations

| Path | Purpose |
|------|---------|
| `packages/trpc/server/routers/_app.ts` | Root app router definition |
| `packages/trpc/server/routers/viewer/_router.tsx` | Main authenticated viewer router (assembles all sub-routers) |
| `packages/trpc/server/routers/publicViewer/_router.tsx` | Public (unauthenticated) router |
| `packages/trpc/server/routers/loggedInViewer/_router.tsx` | Logged-in viewer procedures |
| `packages/trpc/server/routers/viewer/bookings/_router.tsx` | Bookings sub-router |
| `packages/trpc/server/routers/viewer/eventTypes/_router.ts` | Event types sub-router |
| `packages/trpc/server/routers/viewer/slots/_router.tsx` | Slot availability sub-router |
| `packages/trpc/server/routers/features/_router.ts` | Feature flags router |
| `packages/trpc/react/trpc.ts` | Frontend tRPC client setup |
| `packages/trpc/react/index.ts` | Public exports for frontend |
| `apps/web/app/_trpc/` | Next.js App Router tRPC integration |

## Patterns

### Root Router Assembly
**Where:** `packages/trpc/server/routers/_app.ts`
**How it works:** The root router wraps the entire viewer router. All sub-routers are nested under `viewer`.
**Example:**
```ts
// packages/trpc/server/routers/_app.ts
export const appRouter = router({
  viewer: viewerRouter,
});
export type AppRouter = typeof appRouter;
```

### Viewer Router (Hub Router)
**Where:** `packages/trpc/server/routers/viewer/_router.tsx`
**How it works:** Imports and registers all domain-specific sub-routers. This is the main assembly point.
**Example:**
```ts
// packages/trpc/server/routers/viewer/_router.tsx:48-96
export const viewerRouter = router({
  loggedInViewerRouter,
  apps: appsRouter,
  me: meRouter,
  public: publicViewerRouter,
  bookings: bookingsRouter,
  eventTypes: eventTypesRouter,
  availability: availabilityRouter,
  teams: viewerTeamsRouter,
  slots: slotsRouter,
  workflows: workflowsRouter,
  // ... 30+ more sub-routers
});
```

### `_router.tsx` Convention (Procedure Definition)
**Where:** Every sub-router directory (e.g., `packages/trpc/server/routers/viewer/bookings/_router.tsx`)
**How it works:** Each `_router.tsx` file defines a router with procedures. Procedures use dynamic `import()` for handlers to enable code splitting. Input is validated with Zod schemas imported from `.schema.ts` files.
**Example:**
```ts
// packages/trpc/server/routers/viewer/bookings/_router.tsx:25-33
export const bookingsRouter = router({
  get: authedProcedure.input(ZGetInputSchema).query(async ({ input, ctx }) => {
    const { getHandler } = await import("./get.handler");
    return getHandler({ ctx, input });
  }),
  requestReschedule: authedProcedure.input(ZRequestRescheduleInputSchema).mutation(async ({ input, ctx }) => {
    const { requestRescheduleHandler } = await import("./requestReschedule.handler");
    return requestRescheduleHandler({ ctx, input, source: "WEBAPP" });
  }),
});
```

### Procedure Types
**Where:** `packages/trpc/server/procedures/`
**How it works:** Two main base procedures:
- `authedProcedure` -- requires authenticated user session (most procedures)
- `publicProcedure` -- no authentication required (slot queries, public event info)
- `createTeamPbacProcedure` -- team-level permission checks with role requirements

**Example:**
```ts
// packages/trpc/server/routers/viewer/bookings/_router.tsx:98
find: publicProcedure.input(ZFindInputSchema).query(async ({ input, ctx }) => { ... });

// packages/trpc/server/routers/viewer/bookings/_router.tsx:163-166
getWrongAssignmentReports: createTeamPbacProcedure("booking.readTeamBookings", [
  MembershipRole.ADMIN, MembershipRole.OWNER, MembershipRole.MEMBER,
]).input(ZGetWrongAssignmentReportsInputSchema).query(async ({ input }) => { ... });
```

### Input Validation (Zod Schemas)
**Where:** `packages/trpc/server/routers/viewer/<domain>/<procedure>.schema.ts`
**How it works:** Each procedure's input is validated by a Zod schema defined in a companion `.schema.ts` file. The schema file exports a `Z<Name>InputSchema` constant.
**Example:**
```ts
// packages/trpc/server/routers/viewer/bookings/get.schema.ts:45-73
export const ZGetInputSchema = z.object({
  filters: z.object({
    teamIds: z.number().array().optional(),
    status: z.enum(["upcoming", "recurring", "past", "cancelled", "unconfirmed"]).optional(),
    eventTypeIds: z.number().array().optional(),
    attendeeEmail: z.union([z.string(), ZTextFilterValue]).optional(),
    // ...
  }),
  limit: z.number().min(1).max(100),
  offset: z.number().default(0),
  cursor: z.string().optional(),
});
```

### Handler Pattern (Dynamic Import)
**Where:** All `_router.tsx` files
**How it works:** Handlers are dynamically imported inside procedure bodies. This keeps the router file lightweight and enables tree-shaking. The handler file exports a named function.
**Example:**
```ts
// Handler is lazily loaded:
const { getHandler } = await import("./get.handler");
return getHandler({ ctx, input });
```

### Frontend tRPC Client
**Where:** `packages/trpc/react/trpc.ts`
**How it works:** Creates a typed tRPC client with `createTRPCNext`. Routes are split across endpoints using `splitLink` for batch and non-batch requests. Uses `superjson` as the transformer.
**Example:**
```ts
// packages/trpc/react/trpc.ts:50-53
export const trpc = createTRPCNext<AppRouter, NextPageContext>({
  config() {
    const url = typeof window !== "undefined" ? "/api/trpc" : ...;
    return { links: [loggerLink({...}), splitLink({...})], transformer: superjson };
  },
  ssr: false,
});
```

### Frontend Usage
**Where:** `apps/web/` components
**How it works:** Components import `trpc` from `@calcom/trpc/react` and call hooks.
**Example:**
```tsx
// apps/web/components/ui/UsernameAvailability/PremiumTextfield.tsx
const [user] = trpc.viewer.me.get.useSuspenseQuery();
const updateUsername = trpc.viewer.me.updateProfile.useMutation({...});
```

## Conventions

- Every router directory has a `_router.tsx` (or `_router.ts`) file as the entry point
- Schema files are named `<procedure>.schema.ts` and export `Z<Name>InputSchema`
- Handler files are named `<procedure>.handler.ts` and export named handler functions
- Handlers are always dynamically imported (`await import()`) inside procedure bodies
- `authedProcedure` is the default; use `publicProcedure` only for truly public endpoints
- Router keys use camelCase (e.g., `eventTypes`, `bookings`, `loggedInViewerRouter`)
- The `viewer` namespace wraps everything -- frontend paths are `trpc.viewer.<domain>.<proc>`

## Dependencies

- **Uses:** `@trpc/server`, `@trpc/client`, `@trpc/react-query`, `@trpc/next`, `zod`, `superjson`
- **Connects to:** `packages/features/` (handlers call feature logic), `packages/prisma` (via ctx)
- **Used by:** All frontend components via `trpc.viewer.*` hooks

## Gotchas

- The endpoint resolver in `packages/trpc/react/trpc.ts` splits paths by `.` segments to route to different API endpoints -- 2-segment paths go to `viewer`, 3+ segments use the second segment as the endpoint key
- Adding a new router requires: (1) create `_router.tsx`, (2) import and register it in `packages/trpc/server/routers/viewer/_router.tsx`
- `ssr: false` is set globally -- no server-side tRPC rendering
- Stale time is set to 1000ms to deduplicate identical queries within the same render pass
